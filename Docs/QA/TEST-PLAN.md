# StageGame QA 테스트 계획

- 작성일: 2026-10-14 (Asia/Seoul)
- 상태: 확정 계약 v1 검증 계획. 실행·재검증 결과와 남은 gate는 STATUS.md에서 관리.
- 대상: 짧은 판의 Unity 스테이지형 전략게임, 점진적 AI, 재사용 UI/닫기 버튼 프리팹, Excel 기반 게임데이터, 광고 수익화.
- 출시 순서: 원스토어 Android 출시/등급 증빙 → 앱인토스 WebGL. 사용자 원스토어·토스 계정은 준비 완료로 전달받았다. SDK 연동·앱 설정·빌드·심사 승인은 각각 별도 증거가 필요하다.
- QA 쓰기 범위: `Docs/QA/`, `Tests/`만. 이번 작업에서는 문서만 작성하며 Unity 에디터 조작, 다른 담당 파일 수정, 커밋·푸시·외부 발송을 하지 않는다.
- 현재 결과 및 부족한 증거: [STATUS.md](STATUS.md).

## 1. 전제와 검증 시작 조건

2026-10-14 최초 파일 조사에서는 기본 폴더만 확인했다. 이후 생성된 루트 [AGENTS.md](../../AGENTS.md), [계약 v1](../Management/CONTRACT.md), [재미 검증 기준](../Management/VALIDATION.md)을 읽고 이 계획을 구체화했다. QA는 `Docs/QA/`와 `Tests/`만 수정하고, 클라이언트 소유의 Unity 에디터·빌드를 조작하지 않는다. 후속 구현 검증을 시작할 때 지침과 파일 현황을 다시 확인한다.

확정 종목은 **7열 × 6행 중력식 4목**이다. 플레이어 `1`, AI `-1`, 빈 칸 `0`, 열 인덱스 `0~6`이며 가장 낮은 빈 칸에 교대로 둔다. 가로·세로·양 대각선 4개 이상이면 승리하고, 승리 없는 가득 찬 판은 무승부다. 종료 후 착수는 불가하다. 합법 수 순서로 재생되는 중간 국면만 허용하며, 이미 끝난 국면은 시작 배치로 사용할 수 없다.

초기 데이터는 3챕터 × 10개, 총 30스테이지다. Unity `6000.3.15f1`, 세로 `720×1280` 기준, 로컬 AI·최고 해금 스테이지 저장이 MVP 범위다. 온라인 대전·계정·랭킹·결제·클라우드 복원 검증은 MVP에서 해당 없음이다. 실제 구현의 확인 범위는 STATUS.md의 실행 층별 결과를 따른다.

| 선행 자료 | 필요한 내용 | 담당 역할 |
| --- | --- | --- |
| 규칙 명세 | 계약 v1 확보. 재시작·중단·무승부 재도전과 해금 세부 흐름 연결 | 총괄/기획 |
| 스테이지·AI 명세 | 30스테이지·깊이/노드 예산/실수 비율 확보. 실제 난이도 곡선·시간 제한 확인 | 기획/클라이언트 |
| 데이터 계약 | Excel 시트·열·타입·단위·ID·참조, 변환 방법, 버전, 유효 범위 | 데이터 담당 |
| 빌드·지원 환경 | 재현 가능한 빌드 식별자, Unity 버전, 최소 사양, 지원 해상도, Android/WebGL 실행 경로 | 클라이언트/출시 |

부족한 자료는 제품 결함으로 단정하지 않고 `검증 차단 사유`로 기록한다. 명세와 구현이 충돌하거나 같은 입력의 기대 결과를 정할 수 없으면 먼저 판정 기준을 확정한다. 첫 전면광고의 90초 기산점과 유예 이후 첫 경기 간격의 카운터 정의는 구현/기획에서 확인해 정확한 첫 노출 경기를 고정한다.

## 2. 출시 gate

아래 gate는 대상 플랫폼의 **출시 후보 빌드**에서 모두 충족해야 한다. 원스토어 통과 증거를 토스 WebGL 통과로 재사용하지 않는다. 같은 원인에 관한 공통 테스트는 연결할 수 있지만 플랫폼별 실행 증거가 필요하다.

| Gate | 통과 조건 | 필요한 증거 |
| --- | --- | --- |
| G01 규칙·데이터 | 규칙 사례·Excel→배포 정합성 충족, 잘못된 수·비정상 데이터로 상태 손상 없음. 30스테이지의 승리 해금이 불가능한 초기 국면으로 막히지 않음 | 명세/데이터 버전, 실행 로그, 각 스테이지의 실제 정책 승리 예시 및 미확인 범위 |
| G02 결함 | 열린 치명·높음 결함 0건. 수정 결함은 같은 출시 후보에서 재검증 완료 | 결함 목록, 심각도 근거, 수정 빌드, 재검증 결과 |
| G03 실기기 빌드 | Android 실제 기기에서 설치·첫 실행·업데이트·핵심 플레이 통과. WebGL은 실제 대상 호스트/컨테이너와 지원 모바일 기기에서 핵심 흐름 통과 | 빌드 파일/배포 주소 식별자, 기기·OS·호스트 버전, 실행 로그·영상 |
| G04 테스트 광고 | 각 플랫폼에서 승인된 테스트 광고 또는 공식 테스트 모드로 성공·실패·취소·오프라인·복귀 흐름 검증. 실광고로 QA하지 않음 | SDK/어댑터 버전, 테스트 모드 증거, 호출·이벤트 기록. 모의 광고만으로는 gate 통과 불가 |
| G05 보상 일관성 | 보상 대상 완료 1회당 정확히 1회 지급. 중복·지연·역순 이벤트와 재실행에도 총 지급 1회. 실패·취소는 계약에 따라 지급되지 않음 | 트랜잭션별 이벤트/저장 전후, 중복 주입 및 복구 실행 기록 |
| G06 사용·복구·성능 | 필수 저장·복원, UI/안전영역, 수명주기 시나리오 통과. 사전 확정한 성능 기준 충족 | 실제 기기 측정, 스크린샷, 복구 기록, 확정 목표 버전 |
| G07 권리·출시 | 사용 자산의 사용·배포 권리와 필요한 고지가 확인되고, 해당 플랫폼 최신 제출 조건·광고/개인정보 처리가 점검됨 | 출처·라이선스 원문/영수증 등 근거, 공식 조건 URL·확인일, 제출 체크리스트 |
| G08 플레이 검토 | 작은 표본 플레이테스트를 수행하고 결과·이탈 사유·수정 결정을 기록. 총괄이 재미·난이도 상태를 검토함 | 익명 집계, 인터뷰 메모, 목표 대비 결과, 출시/수정 판단 |

필수 항목의 `미실행`, `차단`, 근거 없는 `해당 없음`은 통과가 아니다. 열린 결함이 0건이라는 사실만으로 G02나 전체 gate가 통과하지 않는다. 기본 검증 범위를 실행했다는 증거가 함께 있어야 한다. 판정 후 코드·데이터·SDK·빌드 설정이 바뀌면 영향을 받는 gate를 다시 연다.

## 3. 판정·결함 기준

| 판정 | 의미 |
| --- | --- |
| 미실행 | 아직 실행하지 않음. 추정 결과를 적지 않음 |
| 차단 | 실행을 시도했거나 착수 조건을 확인했으나 필요한 명세/빌드/환경/접근이 없음 |
| 통과 | 명시된 기대 결과와 실제 결과가 일치하고 증거가 있음 |
| 실패 | 기대 결과와 다른 실제 동작을 관찰함. 결함 ID 연결 |
| 해당 없음 | 기능·플랫폼 계약상 적용되지 않음을 총괄이 확인하고 근거를 기록함 |

| 심각도 | 예시 | 출시 처리 |
| --- | --- | --- |
| 치명 | 실행 불가, 진행/보상 데이터 광범위 손실, 반복 보상 악용, 핵심 규칙 붕괴 | 수정·재검증 전 차단 |
| 높음 | 불가능한 AI 수, 빈번한 크래시/멈춤, 진행 불가, 보상 누락/중복, 닫을 수 없는 필수 화면 | 수정·재검증 전 차단 |
| 보통 | 우회 가능한 화면 오류, 제한된 성능 저하, 일부 설명·난이도 문제 | 영향·우회·출시 판단 기록 |
| 낮음 | 핵심 조작과 이해를 방해하지 않는 시각적 어긋남·문구 | 우선순위·처리 계획 기록 |

보상·저장 문제의 심각도는 빈도와 피해 범위로 판단한다. 권리 근거 누락이나 지원 플랫폼 미확정 같은 gate 차단은 제품 결함 집계와 별도로 기록한다.

## 4. 테스트 사례

모든 사례의 최초 상태는 **미실행**이다. 각 표의 기대 결과는 확정 명세와 연결해서 구체화한다. 자동화 개수나 반복 횟수만으로 검증 품질을 판정하지 않는다.

AD05·AD08·AD10은 보상 트랜잭션의 멱등성과 저장 내구성을 확인하는 필수 사례다. 종료된 판의 힌트를 새 판에 이월하지 않는다. 힌트 복구 보장 범위는 판 저장 계약에 맞추고, 어떠한 경우에도 같은 판에 두 번 지급하지 않는다. 실패·미준비·취소 때 무료 재도전이나 기본 플레이를 막으면 실패다.

첫 프로토타입은 기본 `no fill`, Editor에서만 모의 완료/실패/중복이 계약이다. 소스에서 빌드 조건을 읽어 검토하고 Editor 실행은 클라이언트 담당 증거를 받는다. 모의 통과는 실제 SDK 연결/수익 연동 완료가 아니다. 각 이벤트가 유효하다는 판단 기준은 SDK/플랫폼 계약과 함께 확인한다.

## 5. 제안 목표와 측정 방법

아래 성능 수치는 **미측정 제안 목표**이며 현재 제품 성능·재미·광고 수익에 관한 결과가 아니다. 총괄이 최소 지원 기기를 정한 뒤 테스트 전에 수치를 확정한다. 재미 목표는 총괄의 `Docs/Management/VALIDATION.md`를 따른다. 결과를 보고 기준을 낮출 경우 원래 결과와 변경 사유를 함께 보존한다.

### 성능·안정성 목표

| 항목 | 제안 목표 | 측정 조건 |
| --- | --- | --- |
| 플레이 프레임 | 최소 지원 기기에서 30 FPS 이상을 목표, p95 프레임 시간 ≤ 33.3ms | 대표/최대 복잡도 각 3분 이상. 광고 화면과 앱 플레이를 구분 |
| AI 응답 | p95 ≤ 500ms, 1회 최대 ≤ 2초 | 난이도별 대표·최악 상태, 실제 기기. p95에는 최소 100회 이상 표본 수 병기 |
| Android 콜드 시작 | 조작 가능까지 각 측정 ≤ 5초 | 후보 빌드, 최소 지원 기기, 5회 모두와 최댓값 보고 |
| WebGL 첫 진입 | 조작 가능까지 각 측정 ≤ 10초 | 제안 조건 10Mbps/RTT 100ms, 캐시 없는 5회. 호스트 제약에 따라 사전 확정 |
| 장시간 안정성 | 30분 실행에서 크래시·ANR·진행 불가 0건 | 지원 플랫폼별 최소 지원/대표 기기, 테스트 광고·복귀 포함 |
| 메모리 | 기기/호스트별 확정 상한 이하, 반복 UI/스테이지 종료 후 지속 증가 없음 | 5분 안정화 후 30분 시계열·동일 상태 복귀 비교. 절대 상한은 미확정 |
| AI 합법성 | 난이도별 1,000상태 이상에서 불가능한 수 0건 | 수동 정답 경계 사례와 다양한 시드 병행. 표본 밖 완전성 증명은 아님 |
| 보상 중복 | 각 중복/종료 경계 시나리오 20회 목표에서 위반 0건 | 정상 별도 거래 지급도 확인. 단순 성공 광고 20회로 대체하지 않음 |

개발 빌드의 프로파일러는 원인 분석에 사용하고 출시 후보와 같은 설정의 빌드에서 최종 체감을 확인한다. 네트워크·열 상태·품질 설정·계측 도구·샘플 수를 기록한다. 타깃 최소 기기와 메모리 한도 미확정 상태에서는 성능 gate를 통과시킬 수 없다.

### 작은 표본 재미 목표

- 목표 표본: 5명, 1인 최소 3판, 익명 P01~P05. 모집 조건은 실제 목표 사용자에 맞춰 총괄이 확정하며 동의 없이 원자료를 외부로 보내지 않는다.
- 총괄 목표: 설명 후 30초 안에 첫 합법 수 4/5명, 관측 판 중앙값 45~120초, 권유 없이 추가 판 시작 3/5명, 패배 이유 납득 4/5명, 보드/광고 버튼 오터치 0건.
- 난이도 목표: 초반은 규칙 학습과 승리 경험, 이후는 선택 고민 증가. 초·중·후반 승패·소요 시간·막힌 지점과 depth/budget/random 설정을 함께 보고 실제 난이도 추세를 검토한다.
- 반드시 실제 분모를 병기한다. 예: `4/5명`과 비율을 함께 쓰고, 이탈·도움 제공·플레이 시간 제한을 기록한다.
- 첫 광고 노출 뒤의 이탈/불쾌감과 보상 선택 이유를 관찰한다. 소수 표본으로 리텐션·수익·모집단의 재미를 입증했다고 쓰지 않는다.
- 표본 수, 관찰 결과, 목표 미달 원인, 다음 수정 하나 이상과 총괄 판단을 남긴다. 수치는 목표이며 출시 후 지표나 통계적 보장이 아니다.

## 6. 환경·증거 및 재현 기록

최소 환경 후보는 Android의 최소 지원 저사양 1대·대표 기기 1대와, WebGL 실제 대상 호스트에서 지원되는 Android/iOS 각 1대다. 지원하지 않는 환경은 근거와 함께 제외한다. 해상도·안전영역은 에디터 시뮬레이션에 더해 실제 기기에서 확인한다. 정확한 기종·OS·호스트 버전은 아직 미확정이다.

각 실행 결과에는 다음을 남긴다.

1. 실행 ID/사례 ID/실행자/시각(Asia/Seoul), 게임 규칙 버전.
2. 코드 식별자(커밋이 없으면 파일 목록·해시), 빌드 파일 해시, Unity·SDK·데이터 버전, 광고 테스트 설정.
3. 플랫폼/실제 기종/OS/화면·안전영역/브라우저·호스트 버전/네트워크·열 상태.
4. 사전 저장·스테이지·시드·입력·주입 이벤트 순서, 재현 단계, 기대/실제 결과.
5. 통과/실패/차단/미실행/해당 없음, 로그·영상·스크린샷·측정 파일 경로, 연결 결함.
6. 실패의 심각도·영향·재현 빈도·담당·수정 후보·재검증 결과.

증거는 실행 시 `Docs/QA/Evidence/<실행 ID>/`에 저장하거나 접근 가능한 산출물 경로를 연결한다. 개인정보·광고 식별자·인증키는 증거에 포함하지 않거나 가린다. 큰 빌드는 외부로 임의 업로드하지 않고 로컬 경로와 해시를 기록한다. 확보한 증거의 색인은 STATUS.md에 둔다.

자동화는 규칙·AI·데이터·보상 중복처럼 반복 가능하고 독립된 기대값이 있는 부분부터 `Tests/`에 추가할 수 있다. 구현 언어와 테스트 실행 방법을 확인하기 전에는 작동 여부를 알 수 없는 테스트 뼈대를 만들지 않는다. 에디터/CI 모의 테스트로 실제 기기·공식 테스트 광고를 대체하지 않는다.

소스 독립 기대값, 규칙 수순, 데이터 변이 입력, 광고 이벤트 순서와 실행 도구는 [Tests/README.md](../../Tests/README.md)에 정리했다. 준비 명세와 실제 실행 로그를 구별한다.

## 7. 1주 일정의 검증 순서

일정은 인력·플랫폼 준비 상태를 가정한 목표다. 기간이 끝났다는 이유로 미실행 항목을 통과시키지 않는다.

| 시점 | 우선 작업 | 완료 근거 |
| --- | --- | --- |
| D1 | 확정 종목·규칙·데이터 계약 반영, 플랫폼 가능성·최소 기기 확정 | 승인된 기준과 실행 가능한 최소 빌드 |
| D2~D3 | 규칙·AI 합법성·데이터·기본 저장, 빌드 조기 확인, D2 첫 5명 플레이 목표 | 첫 실행 결과, 치명/높음 결함 목록, 초기 플레이 관찰 |
| D4 | 테스트 광고/중복 보상/오프라인·종료 경계, 프리팹·해상도 | 광고 연동 및 복구 증거 |
| D5 | 실제 기기 성능·복귀·장시간 실행, 재미 수정 후 재관찰 | 측정값과 관찰·수정 결정 |
| D6 | 수정 확인, 저장 업데이트·데이터 정합성·출시 자료 | 재검증 결과와 출시 후보 식별자 |
| D7 | 후보 최종 핵심 흐름·gate 검토 | 플랫폼별 통과/차단 및 남은 위험 |

후속 총괄 메시지와 구현 자료가 오면 지침을 다시 읽고, 실제 파일/실행 명령을 확인한 후 승인된 범위의 검증부터 시작한다. QA 담당은 발견한 제품 결함을 기록하고 소유 담당에게 전달할 수 있도록 정리하며, 다른 담당 파일이나 Unity 에디터를 직접 수정하지 않는다.
