# 멀티플레이 반응·음악·결과 UI 독립 검토

2026-10-19 KST. 사용자 요청은 멀티 배경음 복원, 착수 지연 개선, 마지막 수 줌인·줌아웃 후 명확한 승패/레이팅 표시와 편한 다시하기·나가기이다. 총괄이 구현·Unity/브라우저 실행을 담당한다. 독립 검토자는 소스를 읽고 전달된 증거를 검토하며 이 문서만 수정한다.

## 초기 소스 확인

- `RankGameApp.RefreshMusic()`는 활성 화면을 `match`와 `lobby`만으로 판단한다. 멀티가 로비를 숨기면 매 `Update()`에서 음악이 정지한다. 기존 AudioSource를 재사용하고 멀티 패널 활성 상태를 포함하는 수정이 적절하다. 음소거·비활성 앱·광고에 따른 정지는 유지해야 한다.
- `OnlineGameController.Place()`는 `sentMove=true` 후 명령을 보내지만 실제 돌은 서버 스냅샷 수신 후에만 그린다. 입력 직후 1개 돌을 예상 표시하면 눈에 보이는 대기는 줄일 수 있다. 서버 승인 지연 자체와는 다른 개선이다.
- `OnlinePanelLayout.Fit()`는 매 캔버스 렌더 시 보드 위치와 `localScale`을 덮어쓴다. 같은 Transform을 임의 코루틴으로 확대하면 레이아웃과 충돌한다. 저장 프리팹의 전용 시각 자식 또는 레이아웃과 합성되는 명시적 연출값을 사용해야 한다.
- 현재 종료 결과와 재대국 알림은 분리돼 있고 두 행동은 같은 하단행에 고정된다. 기존 스크롤 방지·텍스트 높이·최소 터치 검사와 장점을 유지해야 한다.

| 영역 | 기준 |
| --- | --- |
| 음악 | 메뉴→대국→결과→리매치→로비에서 같은 곡 위치 유지. 설정 음소거·백그라운드·광고 정지는 유지 |

| 취소·중복 | 같은 seq 응답에는 예상 표시 유지, 거절·연결 끊김·방/라운드 변경 시 취소. 더블 탭은 1명령, 승인 시 효과음/착수 연출 중복 금지 |

| 종료 연출 | 서버가 정상 four/draw를 확정한 뒤 방+round당 1회. 리매치 요청·상대 퇴장·재접속 상태 갱신에서 반복 금지. 포기/타임아웃/끊김은 가짜 마지막 돌 연출 제외 |
| 연출 취소 | 새 라운드·로비·연결 끊김·비활성화 시 토큰 취소, 보드/입력 원복. 서버 수신은 연출 동안에도 계속 |
| 결과 정보 | 큰 승리/패배/무승부, 별도 확정 레이팅과 부호 있는 변화량. 비레이팅은 변화 없음으로 표시. 결과를 리매치/퇴장/오류 알림이 덮지 않음 |
| 행동 | 다시하기·나가기 같은 하단행, 최소48px. 리매치 양측 동의 유지, 대기 중 나가기 가능. 상대 퇴장 시 다시하기 비활성·나가기 주행동 |
| 화면 적합성 | 한영 320×568 host와 native1080×1920 DPR1 포함. 확대 시 프로필/하단 버튼을 가리지 않고 종료 후 스크롤 없이 모든 행동 노출 |

줌인·줌아웃 총 약0.6~0.9초를 초기 설계 참고치로 제안했다. 이는 사용자 테스트를 통해 입증된 최적값이 아니다. 연출 중에도 나가기를 막지 않고 긴 대기를 추가하지 않는 것이 우선이다.

## 필요한 검증

1. 예상 착수: 즉시 표시, 더블 탭, 동일 seq 반복, 정상 승인, 거절, 낮은 seq, 연결 끊김, 새 round, 다른 방 순서. 기존 상대 마지막 수 흰 강조는 착수 직후 숨고 거절 시 복원돼야 한다.
2. 종료: 내/상대 마지막 돌 승리, 무승부, 시간초과/포기, 같은 종료 반복, 연출 중 상대 리매치/퇴장, 연출 중 새 round/로비/끊김, 이미 종료된 방 재접속.
3. 결과 수치: 서버 확정 rating/delta를 그대로 표시. 승패 양쪽과 무승부·비레이팅·큰 값/음수 delta. 로비 레이팅도 같은 확정값 반영.
4. 음악: 멀티 실제 AudioSource 시간 진행과 최종 출력, 음소거 유지/저장, 포커스 상실/복귀, 광고 정지/재개. `isPlaying`만으로 들림을 확정하지 않음.
5. 지연: 입력→예상 돌 표시와 입력→서버 승인 RTT를 각각 기록. 로컬 2클라이언트의 확정 판·seq·결과 일치 확인. 예상 표시로 RTT가 개선됐다고 기록하지 않음.
6. UI: 한영·일반/짧은 host·DPR1/3 캡처. 최종 상태뿐 아니라 줌 중·반복 종료·리매치 대기·상대 퇴장도 확인.

## 1차 구현 독립 검토

`OnlineMatchFeedback.cs`, `OnlineGameController.cs`, `OnlinePanelLayout.cs`, `MultiplayerUiBuilder.cs`, 음악 조건과 새 `MultiplayerFeedbackTests.cs`를 읽었다. 음악에 멀티 패널 활성 상태를 포함했고 예상 돌은 `pendingCell`/`sentMove`로 확정 보드와 분리돼 있다. 낮은 seq/이전 round 거절, 동일 snapshot에서 예상 표시 유지, 거절/끊김 취소, 5초 무응답 후 공식 재접속 경로가 추가됐다. 확정 착수 차이를 이용하므로 상대 마지막 수 필드로 내 마지막 수를 잘못 선택하지 않는다.

총괄이 실행한 1차 `Client/Evidence/multiplayer-feedback-20261019/unity-tests.xml`을 직접 읽어 10/10 Passed, 실패0/건너뜀0을 확인했다. 이 결과에는 아래 새로 발견한 경로를 확인하는 검사가 아직 없다.

최종 `unity-tests.xml`을 다시 읽어 **13/13 Passed, 실패0, 건너뜀0**을 확인했다. 기존 입력·강조·레이아웃·광고 경계 회귀에 재접속/비활성화, 응답 대기 시간 초과, 가장자리 확대 검사가 추가됐다. 실행 주체는 총괄이며 독립 검토자는 소스와 결과 파일을 확인했다.

## 최종 판정

지적한 5항목이 보완됐으며, 직접 확인한 최종 소스·자동 검사 결과·Unity PNG12장·WebGL PNG5장에서 추가 차단 문제는 발견하지 못했다. 예상 표시가 서버 판정을 변경하지 않고, 짧은 화면의 결과·상태·다시하기/나가기 배치가 유지됨을 확인했다.

실제 WebGL 브라우저 입력과 공개 WSS 대전 검증의 수행자는 총괄이다. 독립 검토자는 전달된 파일을 검토했다. Pages 배포 커밋 `50dee69`는 사용자 푸시 대기 상태로 보고됐으므로 공개 링크 최신화 완료로 기록하지 않는다. 실제 청취·공개 배포를 독립 검토자가 수행하거나 통과시킨 기록도 아니다.
