# 호스트 상단 UI·간단 그래픽·라이선스 QA

기준일 2026-10-14 KST. 최신 상태는 **독립 호스트14/14·QA-009 종결, Client Unity49/49·관련8/8·본문 확대 후 화면1/1, 본문30 최종 빌드/총괄 브라우저 연결 완료**다. Unity 실행들은 중복 범위이며 합산하지 않는다. 아래 사전 감사와 중간 대기/실패 이력은 보존한다. 기존 한영 코어29묶음·Unity42개·QA-008 결과를 새 호스트 기능 통과로 재사용하지 않는다. QA는 Docs/QA/와 Tests/만 수정하며 Unity는 클라이언트, 브라우저는 총괄이 실행한다.

**초기 독립 실행:** `qa-host-pre-v1-20261014`는 **11묶음 통과, 2묶음 실패**다(C# 6/7, JS 5/6). 구현 중 스냅샷이며 최종 승인 결과가 아니다. 비정상 수치 경계의 QA-009를 기록했다.

## 수정 전 관찰

- WebGL `StageGamePortrait/index.html`은 CSS `env(safe-area-inset-*)`로 패딩/가용 크기를 정한다. `SafeAreaFitter`는 Unity `Screen.safeArea`와 가용 Rect를 처리한다. **호스트 뒤로/닫기 UI의 점유 영역을 입력받는 경로는 아직 없다.** 실제 Toss UI 높이·적용 방식은 추정하지 않는다.
- 고정 720×1280 구성을 전체 축소하는 현재 방식에서 일반 버튼 100단위는 320×568에 약 **44.38px**다. 예를 들어 상단 예약 56px를 별도로 빼면 가용 높이 512px, 버튼은 **40px**가 된다. 이는 고정 비율의 산술 예시이며 실제 Toss 측정값이 아니다. 기존 자료의 320폭 보드 열 영역도 39.05px여서 일반 버튼과 별도로 검사한다.
- 따라서 ‘프리팹 버튼 100 이상’이나 ‘canvas가 viewport 안에 있음’만으로 새 요구를 통과시키지 않는다. 최종 화면 좌표에서 버튼/닫기/라이선스 링크의 hitbox와 게임 열 입력을 확인해야 한다. 짧은 화면을 전체 축소해 글자·터치를 작게 만드는 문제를 검출한다.
- 현재 설정 라이선스 항목은 `LocalizationBuilder`가 535×100의 큰 보조 버튼으로 배치한다. 본문은 별도 모달의 수직 `ScrollRect`·Mask·ContentSizeFitter에 들어 있다. 작은 글자/약한 시각 강조와 충분한 클릭 영역은 별개 조건으로 검사한다.
- UI는 저장된 AppRoot/화면 프리팹과 직렬화된 참조를 사용한다. 새 그래픽은 제작 출처·생성 원본·저장 이미지/스프라이트·참조를 확인한다. 모양의 일관성, 작은 크기에서 식별 가능 여부는 새 캡처가 나온 뒤 확인한다.

## 계약 수신 후 고정할 판정 기준

`Client/HOST-UI-REQUEST.json`과 `Docs/Design/HOST-UI.md`가 아직 없던 시점의 감사다. 계약이 생기면 아래를 확정하고 실제 구현만 독립 검사한다.

- 호스트 inset 단위(CSS px/Unity 좌표), 좌표 원점, 전체 상단 높이에 노치가 포함되는지, 이미 호스트가 viewport를 줄였는지, 입력 없음/0/갱신/해제의 의미.
- 안전영역 공제 소유층과 결합 규칙. 포함된 노치/호스트 높이를 두 번 더하거나, CSS와 Unity에서 같은 영역을 두 번 빼지 않는 독립 기대값을 정한다.
- 최소 지원 viewport/예약 영역, 일반 버튼과 보드 열의 hitbox 기준, 가용 공간이 부족한 경우의 배치 규칙. 44px 요구를 충족하지 않는 조건은 명시하고 통과로 처리하지 않는다.

### 수신한 총괄 결정

- `Docs/Management/CONTRACT.md` 및 총괄 전달에 따라 **호스트/기기 상단 inset 아래 64 CSS px를 추가 예약**한다. 64는 StageGame 제품 설계값이며 공식 Toss 버튼 높이나 실기기 측정값이 아니다.
- 배경/캔버스는 전체 화면에 두고 게임 UI 전체(모달 포함)를 예약 영역 아래에 배치한다. 같은 안전영역을 CSS와 Unity에서 중복 공제하지 않고, CSS 좌표와 캔버스 렌더 크기의 실제 비율로 변환한다. 단독 Android에는 Toss 추가 예약을 적용하지 않는다.
- 계약을 반영한 산술 경계: 기존 100단위 버튼을 그대로 전체 축소하면 **320×568, top 0 + 추가 64 → 39.375px**, **top 44 + 추가 64 → 35.9375px**다(다른 여백 0 가정). 최종 hitbox 44px를 보장하려면 이 단순 전체 축소와 다른 배치/입력 영역 처리가 필요하다.
- `Client/HOST-UI-REQUEST.json`은 아직 질문/준비 상태다. 구현 입력 API·결합 규칙·최소 지원 크기가 확정되는 대로 실제 소스 독립 검사와 최종 브라우저 측정에 연결한다. [기획 검토](../Design/HOST-UI.md)의 모의/실환경 구분을 유지한다.

### 구현 중 소스 검토

`SoftUiBuilder.cs`의 초안은 새 폴더에 둥근 사각형/돌 스프라이트를 생성하고 기존 이미지가 있으면 덮어쓰지 않는다. 저장 프리팹의 스프라이트 참조를 바꾸며 라이선스 버튼은 배경을 투명하게 하고 라벨을 24단위로 줄인다. 검토 시점에는 생성 폴더/산출물이 없었으므로 **그래픽 생성·저장 참조·최종 hitbox 통과로 기록하지 않는다**. 특히 24단위 글자도 전체 축소를 적용하면 작아지므로 최종 표시 크기를 확인한다.

## 구현 중 독립 검사 — qa-host-pre-v1

명령 `Tests/run-host-independent.ps1 -RunId qa-host-pre-v1-20261014`. [C# 결과](Evidence/qa-host-pre-v1-20261014/geometry-results.json) · [JS/브리지 결과](Evidence/qa-host-pre-v1-20261014/bridge-results.json) · [소스 해시](Evidence/qa-host-pre-v1-20261014/source-manifest.json). 실행 중 스냅샷 대상 파일 변경은 없었다.

- 실제 `HostLayout.cs`를 좁은 숫자 API 대체 구현과 함께 .NET으로 실행했다. 64 한 번 적용, OS/CSS 각 변 max, 서로 다른 가로/세로 변환비, controlsBottom+8과의 max, 정상/음수/과대 inset의 영역 계산, 390→320→390 고정 기대값은 통과했다.
- 실제 `host-layout.js`·`HostInsets.jslib`를 Node VM의 명시적 DOM/event/HEAPF32 대체 환경에서 실행했다. CSS fallback, supplied 우선, JS NaN/Infinity 정리, 모의 호스트 분리, resize 재조회, 포인터 순서와 DPR 중복 곱셈 없음은 통과했다. 브라우저는 실행하지 않았다.
- **실패 1:** `HostLayout.ContentArea`에 NaN inset을 직접 주면 출력 Rect에 NaN이 남는다. 일반 JS NaN 입력은 앞단에서 0으로 정리되므로 이 직접 C# 호출 실패를 정상 SDK 경로의 재현으로 주장하지 않는다.
- **실패 2:** `setInsets`에 JS에서는 유한한 `1e300`을 넣으면 그대로 유지되며 jslib의 float32 쓰기에서 Infinity가 된다. C#의 이번 Infinity 사례는 clamp되어 빈 영역이 됐으므로 ‘이 경로로 NaN 발생’이라고 합쳐 쓰지 않는다. 브리지에서 표현 가능한/화면 범위의 유효값으로 제한하는 처리가 필요하다.
- 0 가용 영역 계산이 음수 없이 끝난 사실만 확인했다. `SafeAreaFitter`는 가용 폭/높이가 0이면 스케일 갱신을 생략하므로 이전 콘텐츠 표시·레이캐스트가 남는지, 해당 상태가 지원 범위인지 최종 UI 검사에서 구분한다.
